結論

有力な見落としが1件ありました: Udonarium @ HKTRPG
機能だけでなく、弱い回線を意識したP2P復旧策を独自実装しているため、Axe・Lycorisに続く第三候補へ加えます。
ただし中央WebSocket Relayではなく、通信の最終評価には実回線試験が必要です。

GitHubのforkを明示的に含めた検索と主要系統のfork一覧をたどると、通常検索から漏れていた多数の私家版が見つかりました。その大半は本家・Lily・With Flyの通信をそのまま使う機能特化版、同期しているだけのfork、配布補助でした。通信方式そのものが新しい候補は、既知のLycoris Relay、Udonite、Axe以外には確認できませんでした。

一方、HKTRPG版はSkyWay P2Pのままですが、回線断・高遅延・不完全メッシュ・SkyWay SDKの一時エラーから復旧するための実装が厚く、公開デモと活発な更新もあります。P2Pをどこまで安定化できるかという観点では、Axeと別方向から本気で取り組んでいる候補です。

探索方法

  • GitHub repository検索でudonariumを名前・説明・READMEから検索し、更新日の新しい順に確認
  • 通常除外されるforkをfork:trueで明示的に含め、2024～2026年更新を重点確認
  • 本家、Udonarium Lily、Udonarium with Fly、Axe、Lycorisのfork一覧をGitHub APIで直接取得
  • WebSocket、Relay、Socket.IO、Client/Server、SkyWay 2023等の通信語でも再検索
  • READMEだけで判断せず、有力候補のpackage.json、通信設定、通信ソース、テストを確認
  • 更新日だけが新しい上流同期、素材・変換ツール、個別システム専用版を正式候補から分離

GitHub上の非公開リポジトリ、GitHub外だけで配布されるソース非公開版、検索語にUdonariumを含まない独立再実装は対象外です。

最有力追加候補: Udonarium @ HKTRPG

HKTRPG/UdonariumWithFlyは、NanasuNANA版With Flyから派生した、香港TRPGコミュニティ向けの大規模改修です。公開デモはz01.hktrpg.comです。繁体字・簡体字・英語・日本語を実行中に切り替えられます。

機能面

  • GM / User / Guestのロール別入室、パスワード、招待リンク、プレイヤー権限
  • 照明、視界、壁、FoW、場面ツール、戦闘トラッカー
  • 2Dモード、天候、画像エフェクト、状態・オーラ・死亡表示
  • キーボード操作、Undo / Redo、経路移動、Ping、複数選択
  • プリセット場面、シナリオ文章、多軌BGM、ココフォリア互換キャラJSON
  • 画像・動画・PDFを扱えるノート、handout、自分だけに見えるメモ
  • Chrome / EdgeのFile System Access APIによるルームZIP自動保存
  • モバイルUI、PWA更新通知、初回チュートリアル

標準ダークテーマは確認できませんでした。この点ではAxeが明確に優位です。またAngular 20で比較的新しいものの、AxeのAngular 22 / TypeScript 6ほど全面的な再設計ではなく、With Fly系の大規模拡張です。

通信面で確認した独自対策

  • 回線速度別の切断猶予: 通常8秒、3G相当10秒、2G相当15秒待ち、短いDataChannel断を即切断としません。
  • 購読再試行: SkyWayのpublicationが残っている一時的なSDK・ICEエラーでは、通常2.5秒、3G相当3.5秒、2G相当5秒後に再購読します。
  • ルームメンバー復元: room memberのfatal error時に、退出扱いへ落とす前に再参加とDataStream再公開を試みます。
  • ルーム再オープン: 最後に成功した部屋を覚え、切断・timeout・一部の認証・サーバーエラー時に再オープンします。再試行間隔は3秒から最大60秒へ増加します。
  • メッシュ修復: 5秒周期で部屋メンバーと開いているDataChannelを比較し、欠けた接続をつなぎ直します。45秒以上半開きの接続は再試行対象にします。
  • stale検出: 45秒以上受信がなくhealthが低いDataChannelをリサイクルします。
  • 高遅延時のsurvival mesh: 5人以上の部屋でRTTが2秒を超える不完全メッシュでは、直接接続を1本に抑え、接続済みピアをhubとして転送する方針があります。4人以下は完全メッシュを維持します。
  • ピア経由転送: TTL付きデータを他の接続済みピアへfan-outし、不完全メッシュを補います。
  • 送信優先制御: オブジェクト更新・削除やカーソルを、大きなファイル転送より優先します。未開通DataChannel宛ての送信を一時保留し、開通後に流します。
  • 診断: ping、health、ICE candidate種別、接続・警告履歴を診断用に収集します。
評価上の注意: これらは中央サーバーRelayではなく、ブラウザ同士のP2Pを粘り強く修復する仕組みです。2者間に直接・TURN・第三ピア経由のどの経路も成立しない場合は救済できません。また5人未満では高遅延時のhub化を使わないため、少人数卓では主に再購読・再参加・メッシュ修復が効きます。

保存と復旧

フォルダを一度許可すると、変更後5秒の待機、成功保存間隔30秒以上で、部屋ごとのZIPとメタ情報を自動上書きします。退室、部屋切替、再読込、PWA更新時には即時保存を試みます。これは通信を安定させるものではありませんが、P2P卓が分断・消失した場合の復旧保険として強力です。

通信方式の再比較

候補経路主な復旧策中央の正本今回の評価
Lycoris Relay自前VPSへのHTTPS/WSSWebSocket再接続、サーバースナップショット、メディア再取得あり経路予測性と中央復旧で最有力
AxeWebRTC直接 / TURN / 一時ピア転送25秒stale、自動再接続、ルーム再参加、手動再同期、IndexedDB自動保存なし現代的基盤と復旧UXを含む本命
HKTRPGWebRTC直接 / TURN / ピアhub転送回線別猶予、購読・ルーム再参加、5秒メッシュ修復、再オープン、フォルダ自動保存なし第三候補。弱回線への適応実装が独特
本家 / Lily / With Fly / Switch等WebRTC直接 / TURN系統により自動再接続・手動再接続なし新しい通信解決策としての優先度は低い
UdoniteSocket.IOで中央サーバーサーバー状態・DBあり構造は有力だが、更新と運用基盤が古い

仕様だけから安定性の順位を確定することはできません。Lycorisは経路を単純化し、AxeとHKTRPGはP2Pの失敗を検知・修復します。問題のある参加者の回線で、どの方式が実際に成立するかが最終判断になります。

今後の検証対象

正式な実回線試験は、次の三候補までに絞るのが妥当です。

  1. Lycoris WebSocket Relay: 中央Relay方式の基準
  2. Udonarium Axe: 現代的なP2P復旧方式と標準ダークテーマの本命
  3. Udonarium @ HKTRPG: survival mesh・自動再参加・自動フォルダ保存を持つ追加候補
推奨手順: まずこちらでHKTRPG版のビルドと2ブラウザ同期を確認します。ローカル基準試験に通った場合だけ、通信の弱い卓メンバーへ30分試験をお願いし、試験負担を不必要に増やさないようにします。

HKTRPG版が合格しても、ダークテーマ、リプレイ、コードの現代化ではAxe、中央復旧ではLycorisが優位です。採用は接続成功率を最優先し、合格候補が複数あった場合に機能・保守性で決めます。
